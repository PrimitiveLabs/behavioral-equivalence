# Cloud liveness and preemption

A polling timeout does not establish that cloud work failed. Resume the existing handle or inspect current containers. Do not submit another fit because a local CLI session disconnected, a report is not yet committed, or observation timed out.

A call-graph or function-call summary can retain failed attempt markers while the same logical input restarts after preemption. In the current training campaign, read-only task details explicitly identify preemption, while input start timestamps can be later than the retained failed-attempt end timestamps. These records cannot justify a duplicate recovery. Current logs, container state and updated input metadata must be reconciled first. The recorded diagnosis is `reports/preflight/human-preemption-diagnosis.json`.

The frozen training controller saves epoch metrics and the best model, but does not save optimizer and RNG state for resuming a partial fit. Platform restart can therefore repeat training. Do not skip epochs or reuse a best checkpoint as if it included the missing optimizer state. A future checkpointing change requires a new source identity and explicit training-protocol comparison. Existing source-bound completed models remain valid artifacts under their recorded execution.

Timeout-based reservations are planning controls, not provider-enforced lifetime spending limits. Preemptions, startup, usage above requests, and billing delays require ongoing reconciliation. Avoid stopping unrelated apps, and preserve completed artifacts when investigating this research campaign. Distinguish a remote function-timeout exception from a client observation timeout when interpreting SDK results.
